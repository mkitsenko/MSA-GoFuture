## IAM

- Управление доступом и ролями для аутентификации будет организовано через Keycloak.
- Авторизация будет организована на уровне ролей и выделения доступа через связь для каждого объекта с ролью: Объект <-> Роль (Многие-ко-Многим)
- Предположение организовать ограниченное "нерасширямое" количество прав, для каждой Роли выделить набор и вычислять уровень доступ по битовой маске.

  Например:
    ```
    [Flags]
    public enum Access
    {
        Read = 1,
        Edit = 2,
        Delete = 4,
        Manage = 8
    }
    
    Full Control = Access.Read | Access.Edit | Access.Delete | Access.Manage;
    ```
- При аутентификации будет вычислять принадлежность пользователя к Ролям и шифроваться в JWT токене.
- Доступ будет вычислять по этому токену.

## Мульти-тенантность

### Набор БД для партнера

Реализовать подход 1 Набор БД - 1 партнель для всех микросервисов.

#### Плюсы:
- Удобно разделять доступы и переносить БД, не задевая данные других партнеров
#### Минусы:
- При 1000 партнеров будет гигантское колчиство баз данных

   #### **Вариант не подходит**

### Добавление поля TenantID

- В keycloak для Партнера выделяться свой realm для управления только его доступами и ролями
- Привязать каждый домен организации к TenantId
- Добавить в каждую таблицу TenantID
- Реализовать чтобы поле TenantID было в составном уникальном ключе каждой записи
- TenenId будет зашифрован в JWT токене

Для каждого тенанта будет выделен свой поддомен:
- company1.gofuture.com
- company2.gofuture.com

При аутентификации по домену организации будет определяться тенант.

#### Плюсы:
- Меньшее количество БД - проще управлять 
#### Минусы:
- Тяжелее управлять данными конкретного тенанта, например, бэкап только этого тенанта.
